# 개발 기록 · 빌드 19–40

기존 README에 있던 빌드별 구현·진단 기록을 보관한 문서입니다. 아래 설명과 테스트 수치는 작성 당시 기준이며, 현재 사용법은 [README](../README.md), 프록시 설정은 [프록시 안내](PROXY.md)를 참고하세요. 이후 변경 사항은 [GitHub Releases](https://github.com/04pril/BitChord-iOS/releases)에서 확인할 수 있습니다.

## YouTube AAC 첫 재생 최적화 (빌드 23)

빌드 20은 캐시가 없는 구간의 음수 길이를 다운로드 시작 위치로 사용해 HTTP 416과 재생 실패가 발생할 수 있습니다. 빌드 21은 기존 `cachedPrefixBytes()`로 시작 위치를 계산하고 구독 단계에서도 음수 위치를 거부합니다. 빌드 20 대신 21 이상을 사용하세요.

YouTube에서 제공하는 AAC/MP4 HTTP 스트림에 독립 캐시 수신을 적용합니다. 빌드 22부터 전체 크기가 4MiB 이하이면 파일 전체를 대상으로 하고, 그보다 큰 파일은 첫 1MiB만 대상으로 합니다. AVFoundation의 짧은 탐색 요청이 취소돼도 선행 수신은 유지되며, 같은 범위의 읽기는 진행 중인 fetch를 공유합니다. 첫 데이터가 준비되면 바로 전달하고 전체 수신 완료를 기다리지 않습니다.

곡이나 소스를 교체하거나 로딩을 취소하면 선행 수신도 취소합니다. Opus, 외부 음원, HLS, 로컬 파일에는 이 정책을 적용하지 않습니다. 기존 콘텐츠 길이 검사와 YouTube MP4 duration 보정은 유지합니다. `YouTube AAC opening warmup`과 `opening fetch shared` 로그로 동작을 확인할 수 있습니다. 실제 속도 개선 폭은 실기기 비교가 필요합니다.

빌드 23은 같은 에셋을 공유하는 미리 열기와 실제 재생의 선행 수신 소유권을 분리합니다. 한 소비자가 취소돼도 다른 소비자가 남아 있으면 수신을 유지하며, 마지막 소비자가 놓으면 취소합니다. 다시 사용하는 에셋은 선행 수신을 재시작할 수 있습니다. `opening warmup playback users`와 `opening warmup policy` 로그로 소비자 수와 적용 조건을 확인합니다.

## 애드온 우선의 여러 곡 준비와 모바일 옵션 (빌드 40)

**애드온 우선 재생**도 연속 재생 우선과 같이 최대 다음 4곡의 애드온 음원을 미리 찾고 준비합니다. 일반 Wi-Fi에서는 바로 다음 곡 전체를 캐싱하고, 뒤의 최대 3곡은 각각 앞부분 최대 2MiB를 준비합니다. 현재 곡이 재생되기 시작한 뒤 작업하며, 애드온 음원이 없으면 YouTube 백업을 사용합니다. 무손실 여부는 선택한 음질·애드온의 실제 응답·검증 결과에 따릅니다.

두 모드의 펼침 메뉴에 **모바일 데이터로 다음 곡 전체 준비**를 추가했습니다. 기본값은 꺼짐이며, 모바일·핫스폿·데이터 절약 연결에서는 앞부분만 준비합니다. 켜면 이 연결에서도 바로 다음 곡 전체를 미리 받습니다. 뒤의 곡까지 모두 다운로드하지는 않으며 데이터 사용량이 늘 수 있습니다. 선택값은 앱 재실행·백업 복원 후에도 유지합니다.

준비된 애드온 음원은 조회를 반복하지 않고 바로 사용합니다. 준비 중인 곡을 눌렀을 때는 재생 요청부터 선택한 5·12·15·20초까지만 기다리고, 시간이 끝나면 애드온 대기를 다시 시작하지 않고 YouTube로 넘어갑니다. 뒤늦은 준비 결과가 현재 재생 중인 음원을 자동으로 바꾸지 않습니다. 빠른 재생은 계속 YouTube만 사용합니다.

`source queue plan` 로그에 모드·준비 곡 수·다음 곡 전체 준비 여부를 표시합니다. `scripts/test-source-queue.sh`는 iOS Simulator 없이 실제 앱의 source factory·캐시·타임아웃 코드를 Mac에서 실행하고, 원격 서버만 로컬 대역으로 바꿔 8개 시나리오를 검증합니다. 실제 iPhone의 출력·UI 확인과는 구분합니다.

## 재생 모드 점검과 테스트 도구 (빌드 39)

설정 → 진단 → **전체 로그 기록 → 재생 테스트 → 재생 캐시 지우기**는 재생을 멈춘 뒤 스트리밍 파일과 미리 열린 재생 항목·다음 곡·강제 음원 선택을 비웁니다. 재생 목록, 다운로드와 가져온 파일은 유지하며 다음 재생은 캐시 없이 다시 엽니다. 기존 저장 공간의 캐시 삭제도 같은 경로를 사용합니다. 음원 주소 조회 결과나 로그인 상태까지 초기화하는 기능은 아닙니다.

전체 로그 내보내기 첫머리와 곡별 로그 복사에 현재 선택 모드·유효 자동 전환·저장된 자동 전환 값·대기 시간·Wi-Fi/모바일 음질을 표시합니다. 기록을 켠 상태에서 설정을 바꾸면 변경 시점도 남고, 각 소스 요청에도 실제 요청 모드가 찍힙니다. 내보내기 문맥은 내보낸 순간의 설정이며 과거 기록의 설정을 소급해 설명하지 않습니다. 로그 기록은 계속 기본 꺼짐입니다.

빌드 38 실기기 로그의 Sour Grapes에서 다른 가수의 커버 앨범이 선택되는 것을 확인했습니다. 제목·가수 정규화가 한글·중문을 지우던 부분을 Unicode 문자·숫자를 보존하도록 바꾸고, 다른 가수의 커버·카라오케·헌정 음반 표기가 있으면 길이가 같아도 거부합니다. 이 후보로 오선택을 재현한 테스트는 수정 후 원곡을 선택합니다. 표기가 없고 메타데이터도 같은 다른 녹음까지 식별한다는 보장은 아닙니다.

모드 변경 전 시작한 열기/크로스페이드 준비의 늦은 완료가 이전 소스를 재등록하지 못하게 하고, 자동 전환 설정 변경은 준비된 다음 곡을 재사용하게 했습니다. 이미 끝난 애드온 결과를 디코더가 열리는 동안 잠시 유지하며, 함께 듣기에서 선택한 음질을 보존합니다. 잘못된 대기 시간 입력은 화면과 저장값 모두 12초로 맞춥니다.

전체 BitChordKit 테스트 3,031개 중 2,969개 통과·62개 생략·실패 0개를 확인했습니다. 캐시 삭제·로그 문맥 추가 후 관련 테스트 53개도 통과했습니다. iOS 앱과 테스트 번들은 컴파일 확인하며, 이 Mac에는 iOS 시뮬레이터 런타임이 없어 iOS 화면 테스트는 실행하지 못했습니다. 실제 iPhone의 출력 싱크와 모드별 조작은 사용자 확인이 필요합니다.

## 음원 재생 방식 (빌드 38)

설정 → **음원 서비스 → 음원 재생 방식**에서 선택합니다. 선택한 모드 바로 아래에 세부 설정이 펼쳐집니다.

| 모드 | 동작 | 펼쳐지는 설정 |
|---|---|---|
| 빠른 재생 | YouTube만 사용. 애드온 연결 상태와 무관하게 조회·자동 전환을 건너뜁니다. | 음질은 기존 Wi-Fi·모바일 음질에서 낮음·보통·높음 선택 |
| 연속 재생 우선 | 새 곡은 YouTube로 빠르게 시작하고 다음 곡의 애드온 음원을 미리 준비합니다. 준비된 다음 곡은 애드온 음원으로 바로 시작할 수 있습니다. | **재생 중 자동 음원 전환**, 기본 **켬** |
| 애드온 우선 재생 | 애드온 탐색과 YouTube 백업을 함께 준비합니다. 대기 안에 검증된 애드온 음원을 확보하면 사용하고, 없거나 제한 시간이 지나면 YouTube로 재생합니다. | **5 / 12 / 15 / 20초**, 기본 **12초** |

연속 재생 우선에서 자동 전환을 꺼도 다음 곡 준비는 계속됩니다. 애드온 우선의 제한 시간은 곡 재생 요청부터 계산하며, YouTube 주소 준비 후 시간을 다시 세지 않습니다. 제한 시간이 지나 YouTube로 시작한 곡은 뒤늦게 자동 전환하지 않습니다. 이 시간은 애드온 대기 한도이며 네트워크·디코더까지 포함한 실제 소리 시작 시간의 보장은 아닙니다. 애드온이 없거나 음원이 없다고 확인되면 일찍 YouTube로 넘어갑니다.

기존 음질 제한·음원 매칭·FLAC 검증·캐시를 유지합니다. 다운로드와 로컬 파일은 기존 경로를 사용합니다. 404와 서버 일시 장애·시간 초과를 구분하며, 502·503·504 또는 시간 초과는 한 번만 추가 시도합니다. 기존 설정의 Off는 애드온을 검색하던 방식이므로 최초 업데이트 시 연속 재생 우선으로 옮깁니다. 새 기본값도 연속 재생 우선입니다. 자동 테스트는 실행하지 않았으며 Release 빌드·IPA 구조·서명을 확인합니다. 실제 재생은 사용자 실기기 확인이 필요합니다.

## 컬러 위젯 제목 간격·굵기 (빌드 37)

컬러 4×2는 제목·가수명을 하나의 높이가 자연스럽게 정해지는 묶음으로 배치합니다. 한 줄 제목에 두 줄 공간을 예약하던 방식을 없애 가수명이 바로 아래에 붙고, 두 줄 제목도 같은 간격을 유지합니다. 컬러 4×2·2×2의 제목은 Medium에서 Semibold로 한 단계 올렸으며 글자 크기와 가수명 굵기는 유지합니다. 위젯 5개와 선택 목록 순서는 빌드 36과 같습니다.

## 컬러 4×2 레이아웃 보정 (빌드 36)

컬러 2×2도 같은 색감·표지 라운드·글리프·폰트 톤으로 구성하고 상단 왼쪽 표지·오른쪽 글리프, 왼쪽 정렬 한 줄 제목·가수명, 하단 재생 버튼으로 별도 배치했습니다. WidgetPod의 Default Artwork / Curved / Liquid Artwork / Track Title·Artist Name 구성을 기준으로 커버 크기와 여백, 제목 두 줄 영역, 가수명, 세 재생 버튼의 중심을 맞췄습니다. 밝은 노란 단색처럼 보이던 배경은 표지의 흐림·보조 색·어두운 하단으로 조정했습니다. Player Icon은 두 개 연결된 8분음표의 Apple Music Glyph 실루엣입니다. 위젯 제목 크기는 고정해 기기 글자 설정 때문에 한 줄로 잘리거나 버튼이 밀리지 않게 했습니다. 원본 3종 위젯의 배치는 유지합니다.

## 컬러 위젯 (빌드 32)

기존 2×2, 4×2, 4×1 위젯은 그대로 두고 컬러 카드를 추가합니다. 위젯 선택 목록은 컬러 4×2 → 컬러 2×2 → 순정 2×2 → 순정 4×2 → 순정 4×1 순서의 총 5개입니다. 컬러 4×1은 목록에서 제외했습니다. 4×2 배경은 표지를 크게 흐린 색이고, 표지 모서리는 한 변의 약 11.5%입니다. 제목은 두 줄까지 가운데 정렬되고, 아티스트는 그 바로 아래에 붙습니다. 이전·재생·다음은 오른쪽 칸에 넓게 놓입니다.

## 위젯 그룹 선택 (빌드 30)

재서명이 `group.com.music.bitchord`를 여러 개의 번호 그룹으로 바꿔도, 앱과 위젯 서명에 같이 들어 있는 그룹을 이름순으로 시도합니다. 컨테이너가 열리는 첫 그룹을 양쪽에 같이 씁니다. 위젯에 없는 그룹은 고르지 않습니다. 교집합의 어떤 그룹도 컨테이너를 주지 않으면 프로비저닝 프로필에 그 그룹이 없는 것이므로, 그룹을 하나 등록해 앱과 위젯에 같은 ID로 서명해야 합니다.

## 무손실 준비와 재생 조작 (빌드 29)

자동 FLAC 업그레이드는 정확한 중간 탐색용 플레이어에 연결하기 전에 해당 파일을 캐시에 준비합니다. 로그에서는 헤더·탐색 지점 준비 이후 정밀 FLAC 항목이 나머지 파일을 읽는 동안 조작이 밀렸습니다. 정확히 어느 네이티브 함수에서 멈췄는지는 로그만으로 확정하지 못했으므로, 네트워크 대기를 플레이어 연결 이전으로 옮깁니다. 정밀 FLAC의 길이·트랙 시간 범위도 비동기로 먼저 준비합니다. 현재 음원은 계속 재생하며, 캐시 준비는 최대 128MiB와 현재 캐시 용량 내에서 60초까지 진행합니다. 준비가 끝나면 같은 곡 재생 중 전환을 시도하고, 일시적인 준비 실패에는 한 번 더 시도합니다. 범위를 넘는 파일이나 실패한 후보는 무조건 강제 전환하지 않고 보관합니다. 음질·PCM·출력 코덱은 변경하지 않습니다.

정지 시 두 재생기를 모두 먼저 멈추고 음질 전환을 취소합니다. 이전 전환 작업의 늦은 정리 코드가 새 곡의 재생기를 조작하지 않도록 전환 세대를 확인합니다. 항목 제거 시 탐색·프리롤도 취소합니다. 통계 수집은 이미 비동기로 확보한 오디오 트랙이 있으면 동기 player-item 트랙 조회를 생략합니다. 준비 로그와 실기기의 곡 넘기기·정지·실제 음원 전환을 비교해야 개선 효과를 확인할 수 있습니다.

## 로그인 브라우저 프록시 (빌드 28)

Google 로그인은 앱 내부 `WKWebView`에서 진행됩니다. WebKit은 URLSession 설정을 상속하지 않으므로, 로그인에 사용하는 기본 `WKWebsiteDataStore`에도 이번 실행의 프록시를 별도로 설정합니다. 웹 뷰 생성 전에 동일한 WireGuard 로컬 SOCKS5 또는 외부 HTTP/HTTPS/SOCKS5 프록시를 적용하며 직접 연결로의 폴백은 끕니다. 프록시 설정 실패 시 페이지를 열지 않고 안내를 표시합니다. Google 로그인 쿠키·페이지·확인 방식은 유지합니다.

프록시를 켜거나 연결 설정을 바꾸면 앱을 완전히 종료하고 다시 연 뒤 로그인하세요. 프록시가 꺼진 경우에는 기존 직접 연결을 사용합니다. 진단의 `proxy.browser`는 설정 적용 횟수이며 실제 브라우저 출구 IP를 확인한 결과는 아닙니다. Safari나 별도 시스템 인증 창에는 이 설정이 적용되지 않습니다.

## 준비된 음원으로만 자동 전환 (빌드 27)

자동 음질 업그레이드는 준비된 대기 덱으로 정상 전환할 수 있을 때 적용합니다. 준비 실패나 제한 시간 초과 시 현재 재생을 유지하고 후보를 다음 재생을 위해 보관합니다. 이 경우 이전 음원을 불필요하게 다시 열지 않으며, 업그레이드 표시는 실제 전환과 확인이 끝난 후에 바뀝니다. 사용자가 요청한 일반 소스 교체의 강제 재열기 경로는 실시간 플레이어 위치를 사용합니다.

초기·명시적 탐색은 항목을 플레이어에 연결하고 준비 완료가 된 뒤 요청합니다. 초기 탐색이 남아 있으면 재생 시작을 보류하고, 완료 콜백의 성공 여부를 확인합니다. 이전 탐색·프리롤의 늦은 콜백이 새 요청을 완료 처리하지 않도록 세대를 확인합니다. `seek deferred`, `seek returned success`, `replacement deferred` 로그를 추가했습니다.

전환 제한 시간 초과와 잘못 처리될 수 있던 탐색 경로는 로그·코드에서 확인했지만, 음원 버전 자체의 오프셋이나 이번 변경의 실기기 효과는 추가 로그로 비교해야 합니다.

## 위젯 공유 저장소와 로그 기본값 (빌드 26)

전체 로그 기록은 새 설치에서 기본으로 꺼집니다. 이미 저장된 기록 설정은 유지하므로 진행 중인 로그 수집은 계속됩니다.

앱과 위젯은 실제 코드 서명의 App Group 권한에서 공유 그룹을 선택합니다. 재서명 도구가 그룹 ID를 변경한 경우 원래의 고정 ID만 찾던 경로를 보완합니다. 선택 가능한 그룹이 여러 개면 앱의 그룹 이름에 해당하는 후보를 우선하며, 관련 없는 여러 그룹 중 하나를 임의로 사용하지 않습니다.

재생 정보는 그룹 컨테이너의 원자적 JSON 파일로 쓰고 위젯이 직접 읽습니다. 기존 공유 defaults는 호환 경로로 유지합니다. 곡·표지·재생 상태 변경은 즉시 저장하고 진행률만 바뀌는 기록은 최대 5초에 한 번으로 제한합니다. 빈 위젯은 다시 갱신을 요청합니다.

설정 → 진단 → **위젯 연결**에서 앱의 공유 저장소 읽기·쓰기, 저장된 곡, 마지막 위젯 읽기를 확인하고 현재 재생 정보 전송 및 진단 복사를 할 수 있습니다. 앱의 쓰기 성공과 위젯의 읽기 성공은 구분해서 표시합니다.

앱과 위젯 양쪽의 서명에 같은 App Group 접근 권한이 필요합니다. 권한이 제거되었거나 프로비저닝 프로필이 허용하지 않는 경우 이 코드가 권한을 만들어 주지는 않습니다. 권한 확인은 서명된 Mach-O의 XML 권한 정보를 우선 읽고, 해당 정보가 없으면 Security 함수를 동적으로 조회합니다. 지원 여부와 앱/위젯의 실제 공유는 설치한 서명 조합에서 확인해야 합니다.

## FLAC 헤더 확인과 타입 정정 (빌드 25)

애드온이 실제 FLAC 파일을 `audio/mpeg`로 응답해 AVFoundation에 `public.mp3`가 전달되는 경우를 보완합니다. 새 에셋을 열 때 캐시에 이미 받은 앞부분의 `fLaC` 마커를 확인한 경우에만 콘텐츠 타입을 `org.xiph.flac` / `audio/flac`으로 정정합니다. 추가 네트워크 요청이나 음원 바이트 변경은 하지 않습니다.

`FLAC cached header`에 STREAMINFO의 샘플레이트·채널·비트 깊이·샘플 수와 탐색표 포인트 수를 기록합니다. 최대 256KiB의 캐시된 앞부분만 살피며 메타데이터가 덜 들어왔으면 `metadataComplete=false`로 표시합니다. 정확한 탐색을 위해 에셋을 다시 여는 시각과 당시 캐시된 바이트도 기록합니다. 타입 정정으로 전환 준비 시간이 줄어드는지는 실기기 비교가 필요합니다.

## 전체 로그 기록과 재생 준비 진단 (빌드 24)

설정 → 진단 → **전체 로그 기록**에서 여러 곡의 검색·캐시·플레이어·출력 경로를 하나의 파일로 기록합니다. 기록을 꺼도 파일은 남으며, **전체 로그 파일 공유**는 현재/이전 로그를 시간순으로 합친 고정 복사본을 내보냅니다. **저장된 로그 지우기**로 다음 테스트를 준비할 수 있습니다. 최근 기록은 최대 약 16MiB까지 보관합니다.

재생 요청, 에셋 연결, `playImmediately` 호출, `AVPlayerItem` 준비 상태, `timeControlStatus`와 대기 사유, 첫 버퍼, 오디오 세션 활성화와 출력 경로 변경을 기록합니다. 상태 알림의 메인 큐 전달 지연과 AVFoundation이 읽은 실제 오디오 포맷도 포함합니다. 기존 `first audio` 표기는 실제 출력 측정으로 오해하지 않도록 `player ready and playing`으로 바꿨으며, 시계 움직임 관측과 추정 지연을 별도로 표시합니다. 이 기록은 스피커에서 실제 소리가 난 순간을 측정하지 않습니다.

## 첫 재생 진단 (빌드 19)

- `AV resource request #… started/completed/cancelled`: AVFoundation이 보낸 각 리소스 요청의 오프셋과 처리 시간.
- `AV read #…`: 요청 범위, 총 처리 시간, 디스크 캐시에서 전달한 바이트와 fetch 스트림에서 전달한 바이트, 첫 fetch 데이터까지 기다린 시간.
- `HTTP range #…`: 각 HTTP Range의 요청·응답 헤더·첫 본문 시각과 종료 때의 수신량·전달량·상태.

`fetch stream`은 AudioCacheStore의 진행 중인 fetch에서 전달받은 바이트입니다. 여러 읽기가 같은 fetch를 공유할 수 있으므로 이 수치만으로 각각 별도 네트워크 요청을 했다고 볼 수는 없습니다. 실제 HTTP 요청 수와 대기 시간은 `HTTP range` 로그와 함께 비교하세요.
